# Bounded local four-validator transaction measurement

This runner prepares the next network evidence gate after the application-only fee-journal measurements. Execution requires a fresh resource window from Root. Neither the expired pre-reboot window nor successful offline tests establish a network result.

## Preparation

From the performance worktree, build the three local commands before the scheduled window:

```sh
env GOMAXPROCS=2 nice -n 10 go build -p 1 \
  -o artifacts/chain-performance-20261017/network-bin/ \
  ./cmd/ynx-abci ./cmd/ynx-consensus-perf-fixture ./cmd/ynx-consensus-perf-client
```

Use the existing version-pinned CometBFT executable resolved by `go tool -n cometbft`, then inspect the plan without starting processes:

```sh
node scripts/loadtest/consensus-local-window.mjs \
  --bin-dir artifacts/chain-performance-20261017/network-bin \
  --comet-bin /absolute/path/to/version-pinned/cometbft
```

Only during the newly scheduled window, append `--execute`. The launcher starts 4 CometBFT nodes and 4 persistent ABCI applications, all bound to `127.0.0.1`, with P2P ports 31656–31659, RPC 31757–31760 and ABCI 31858–31861. It refuses occupied ports. Node timing configuration is generated by the existing ephemeral network generator and retained in each node's `config/config.toml`.

The fixture creates 32 fresh sending keys in memory, funds only new test accounts and signs one native transfer per sender. Sender keys are not saved. Four disposable consensus key sets and all node databases live in a fresh local directory. Existing networks, accounts, databases and output directories are never reused. `--count` accepts 1–64; the first scheduled run uses 32.

## Resource and lifecycle limits

- Prebuilt binaries only; compilation is excluded from the window.
- `GOMAXPROCS=1` and nice 10 for each child.
- Active deadline 45 seconds, then up to 15 seconds for shutdown.
- Client setup/workload deadline 10 seconds; 4 workers cover whole submit-and-observe lifetimes.
- Combined sampled child RSS cap 2 GiB; sample interval 250 ms.
- Test data/output cap 128 MiB; each child log capped at 1 MiB.
- Children each have an isolated process group. Shutdown sends SIGINT, waits, then uses SIGKILL only for surviving owned groups. Receipt records PID, exit code/signal, group disappearance, peak RSS/data and the first failure cause.

The caps are monitored at finite intervals, not OS hard quotas. The receipt provides the observed peaks and any violation. A cap violation is a failed run, not a benchmark success. Files are retained for diagnosis; no automatic retry resubmits uncertain transactions.

## Evidence semantics

`transactions-result.json` preserves every transaction outcome and timestamp. Submission, CheckTx acceptance, code-zero inclusion, signed quorum confirmation and final submission counts are separate. Rate denominators use the full workload observation/drain window, excluding setup. This closed-loop 32-transaction smoke is not a saturation or sustained-throughput test.

The client validates all four local genesis files against the manifest's SHA-256 and binds the validator public keys, addresses and voting weights to that genesis. RPC requests are restricted to the four explicit loopback endpoints; proxying, redirects and connections outside the manifest endpoint set are disabled.

For each confirmed transaction it verifies:

1. Raw transaction/hash identity and code-zero result from local RPC.
2. Transaction Merkle inclusion against the signed block header.
3. Actual Ed25519 commit signatures with CometBFT's weighted `VerifyCommitLight`, including header/block/validator-set identity.
4. A readback of that node's persisted application state, including full state validation, matching native transaction fee record at the inclusion height and sender nonce.

`finalSubmitted` increments only after all these checks pass. Submission transport errors retain an unknown outcome and are not retried. Invalid signatures/proofs, rejected transactions, execution failures, missing durability, deadlines and unsubmitted work stay explicit in the report.

Latencies use a client monotonic clock from each individual submission start. P50/P95/P99 include RPC, polling and local verification overhead, with successful sample counts shown. Confirmation latency includes the local durable readback. The same-height Header.AppHash authenticates preceding application state; the current local disk readback is additional local evidence and is not cryptographically bound by that same-height AppHash. A later signed AppHash, cross-node state convergence and abnormal-exit restart are additional gates for subsequent runs.

The launcher saves `window-receipt.json` separately. A successful client result does not prove process cleanup; verify the receipt and fresh PID/port checks. A successful launcher does not establish sustained 1,000 TPS, a 10-minute stability result or public-network acceptance.

## Offline checks

```sh
node --check scripts/loadtest/consensus-local-window.mjs
env GOMAXPROCS=2 nice -n 10 go test -p 1 \
  ./internal/consensus ./cmd/ynx-consensus-perf-fixture ./cmd/ynx-consensus-perf-client \
  -count=1 -timeout=90s
```

Tests exercise real generated signatures and Merkle proofs without starting nodes: equal and unequal voting-power thresholds, insufficient quorum, tampered signatures/weights/transactions/proofs, rejected execution, bounded local inputs, unknown/timeout accounting, actual persistent application readback and tampered state rejection.
