## Durable order/session binding (P06-02 legacy projection)

- `POST /v1/merchant/payment-sessions`: authenticated canonical merchant `invoice` permission; body `{"invoiceId":"<product OR central OR original intent ID>","sourceOrder":"<exact order ID>"}`.
- `GET /v1/merchant/payment-sessions/{sourceOrder}`: authenticated canonical merchant `read` permission; reads the original binding only. Missing receipt returns an error and makes zero provider calls.
- Go: `Service.OpenPaymentSession`, `Service.PaymentSession`, `PaymentSessionInput`, `PaymentSession` in `payment_session.go`.
- `PaymentSession.id == original Invoice.intentId`; this is the authoritative alias within this legacy Pay projection. No second intent/session identity is minted. `invoiceId` is the product ID; `centralInvoiceId` remains the original central ID; `deepLink == ynxpay://invoice/<product invoice ID>`.
- The original Store transaction writes `IdempotencyRecord` under `payment-session:<merchant>:<sourceOrder>`. Its Key preserves the exact raw order ID; ObjectID preserves the original invoice; RequestHash binds product/central/intent/order/original invoice signature. Existing schema and atomic snapshot are reused. One order cannot bind another invoice; one invoice cannot bind another order. Only one owner/process may write this local Store; no multi-host uniqueness is claimed.
- New binding requires an unexpired pending invoice and a valid original registered merchant signature. A signed historical invoice with missing/noncanonical aliases cannot activate a new session. Existing signed history remains readable after expiry; expiry does not reissue or approve funds.
- Response includes `version=1`, `invoiceAuthority=legacy_ed25519_product_projection`, full original public `invoice`, IDs/order/deepLink/status/createdAt/expiresAt, `signedPayload`, `signature`. Public invoice preserves the existing ExpectedPayerHash redaction contract.

The merchant signs the exact UTF-8 bytes obtained by decoding unpadded base64 `signedPayload`; the signature is hex Ed25519. Payload JSON is `{"domain":"YNX_PAY_SESSION_V1","session":<the descriptor with signedPayload and signature empty>}`. Consumers must verify against the independently trusted registered merchant key, require that domain, and compare every outer field to the parsed signed inner session (except the two signature fields). Trusting the response-carried key or only outer fields is insufficient. `TestOpenPaymentSessionBindsOriginalOrderAliasesAndColdRead` verifies raw payload signature and order tamper rejection.

`sourceOrder` is an assertion by the authenticated merchant, not proof of a real Shop order, original buyer, inventory deadline or Shop authority. P07 must check its own original Order and session/current actor before accepting this binding. This descriptor is preview/recovery evidence only; it cannot activate or approve a new V5 asset operation. Pay's absent genesis/unitVersion/current checkpoint/current Wallet policy/dual-PQ issuer evidence must remain NOT_SUPPLIED. No client should fill those fields to manufacture a trusted V5 Invoice.

## P06-08 successor: original Webhook crash and replay semantics

`Deliver` now honors both retry deadlines and terminal dead letters even on direct calls. It commits attempt count and exponential next-at time BEFORE any network request. On lost responses or archival failure, cold restart reads that same reserved budget and original event. The fifth reserved attempt is conservatively persisted as dead letter before dispatch; only an archived successful response changes it to delivered. A crash during that fifth attempt leaves the original outcome uncertain and does not silently restart another five attempts. Redirects are returned without forwarding signed callbacks to another target.

Manual replay uses the existing persisted ParentDeliveryID lineage to preserve the original recipient Event-ID/Delivery-ID and exact business payload; the original V1 signing material binds that event ID, a fresh manual replay timestamp, and original payload hash. Local replay/audit IDs remain distinct. No recipient inbox implementation or exactly-once external effect is claimed: recipients must deduplicate the stable event under their own authority. Historical manual records with different payload hashes remain preserved and require recovery; they are never silently rewritten or treated as a second valid original event.

`acceptSettlement` and `RefreshRefund` enqueue the original signed notification within the SAME original Store transaction as the confirmed business projection. Signing/persistence failure leaves both uncommitted locally, allowing original evidence reconciliation; it does not undo or repeat a remote money action. Repeated enqueue after key rotation finds the existing semantic event and does not mint another event. Original historical missing outbox records are not fabricated/backfilled by this change.

Tests `TestWebhookRetryBudgetSurvivesColdStoreAndDirectCalls`, `TestWebhookPersistsAttemptBeforeSending`, `TestWebhookManualReplayKeepsOriginalSignedEvent`, `TestWebhookOutboxAtomicAndRotationRetainsEvent` use isolated original Store plus TLS HTTP receiver. They cover durable budget read before receiver handling, remote success/local archival failure, cold retry gating, dead-letter cap, stable manual event/body/signature and atomic outbox rollback/rotation. Original retry tests now advance to the actual scheduled next attempt; no failure assertions were removed.

## Whole payment/refund recovery workflow

The original signed settlement controller now records one sealed, invoice-derived dispatch slot before invoking its original provider. It retains the original signed intent/result, payer, transaction, request/operation key and provider identity. A second window or key cannot replace an UNKNOWN operation; `GET /v1/invoices/{id}/payment-outcome` requires a fresh original Pay Gateway assertion and reads the same original operation only. Recovery can outlive the old quote because it does not authorize or resend a new effect. Receipt verification, Wallet proof metadata, original operation confirmation, single receipt claim and Webhook outbox commit in one Store transaction. This closes the previous post-receipt proof-write crash gap. A provider change cannot redirect original-operation readback.

A matching funds event with committed time after invoice expiry is recorded as `late_payment_review`, with an `invoice.late-payment-review` notification, rather than automatic fulfillment. Original paid facts survive repeated queries and cold recovery. The signed result submission path cannot accept a provider receipt for another payer/transaction. Existing original payment/receipt interfaces remain explicitly legacy until CORE supplies its new terms/settle/refund native kinds.

Refund submission durably reserves its original approved Wallet binding and dispatch before the provider call. Response loss remains UNKNOWN across restarts; another key/authorization cannot reopen it or release reserved principal. Unknown refunds do not count as money returned. A known submitted response still requires matching authoritative funds evidence before `refunded`; receipt/transaction claims and outbox are atomic. Integer subtraction bounds prevent concurrent or overflowing aggregate reservations. The original Merchant provider wrapper now forwards the actual AuthorizedRefundAPI under its existing current-member/authority fence; it no longer loses that capability at the real controller boundary.
