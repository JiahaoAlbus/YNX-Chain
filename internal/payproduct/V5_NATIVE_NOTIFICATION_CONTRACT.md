# Original Native Pay event recovery

This extends the existing Pay private service and standalone `apps/pay/native` client. Pay owns its original invoice/proof/operation/outbox journal; Main owns protected review, approval, Member and UNKNOWN submission state. This module adds only a read projection and a durable client notification-reference inbox. No shared Main/Auth/SDK/Core source or old Web UI changes are required.

`NativePayService.InvoiceEvents(ctx, merchant, invoice)` is exposed through the original private handler at `GET /v5/pay/invoices/{merchant}/{invoice}/events`. It reuses `Read` authorization before projection and before returning. Only original `confirmed` operations with retained independently proven effects are included. The event identity is the existing `nativeEventClaim(effect)`, not a new signature or protocol. Each event contains genesis, exact invoice/session/source order, original Native and ABCI hashes, decimal-string member/event/height, kind and effect hash. An original root webhook delivery ID may be linked; manual replay children do not create another event. UNKNOWN, pending and proven failures are excluded. The bounded feed contains at most 1024 references, and exposes no money summary, Member wire, webhook secret, Source grant or approval.

The existing fixed-origin private client reads this endpoint. `NativePayBusinessClient.syncNotifications` first reads the authenticated original Pay bill, obtains the real Source partition/current fence, stages references, checks the original confirmed operation/effect, calls the original product's read-only lookup, commits notification progress and rereads Pay. `events MERCHANT INVOICE` exposes this on the existing normal CLI. Normal summary amounts always come from Pay; callback amounts/status are ignored and `clientIndependentFinality` stays false.

The runtime supplies the optional ports documented in `apps/pay/native/README.md`:

- `notificationInbox`: the packaged `NativePayNotificationInbox` opened at an explicitly selected private external-volume path. The runtime owns cleanup/close, without deleting data on logout.
- `readNotificationScope()`: original Source identity, current actor, genesis, binding digest and synchronous current fence. The Source owner defines the actual binding digest; events/CLI input cannot create it. Rebinding partitions records instead of overwriting the old account's inbox.
- `refreshOriginalProduct(reference,current)`: original Cloud/Shop Source-only lookup by the same `sourceOrder`, returning `{sourceOrder,queryOnly:true}`. It must not create a replacement order/charge, reprice, submit, approve, or replay a funds operation. The Source owner must preserve original authorization on the lookup.

The SQLite inbox stores immutable event references, their digest, partition and a local refreshed flag. It uses a private directory/file, WAL/FULL synchronous transactions, duplicate/conflict checks and Source fences around commits. A changed reference for the same event rolls back the whole batch. Different databases/schema markers are preserved and rejected, without reset/migration. Missing product readers retain pending references across reopen. Crashing after lookup and before progress commit can repeat only that read-only lookup. Progress is not exactly-once delivery, an order-paid acknowledgement, a receipt, authority or finality. Original server/Main UNKNOWN is never replayed from this cache. Private Source retirement clears client bill state; Source-independent archival facts remain in their original owners.

Focused CI reuses `internal/payproduct/testsupport/run_native_workflow.sh` with `PAY_NATIVE_WORKFLOW_SUITE=notifications`, an existing prepared P06 composition and original public fixture directory. Set `TMPDIR`, `GOTMPDIR` and `GOCACHE` explicitly to the external work directory. This runs the existing client controls including notification cases and only `TestNativeInvoiceEvents` on the Go side, without exporting/reexecuting the old 100/30/70 funds workflow. Default full-suite behavior still includes the new cases. Event projector fixtures deliberately assume an already confirmed journal; they are not new H/H+1 or money proof. The prior independently verified temporary Core workflow is retained separately.
