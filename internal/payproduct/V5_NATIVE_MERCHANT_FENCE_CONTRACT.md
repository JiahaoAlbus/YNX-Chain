# Original Pay merchant commit fence for Auth Source

The actual normal callee is `(*Store).CaptureNativeMerchantFence(productMerchantID,principal,recipient string,invoiceMemberRequired bool) (*NativeMerchantFence,error)` in `merchant_fence.go`. Use the same original Pay Store already owned by the service/factory; do not open another Store, infer an issuer from payout, create another membership table or construct a Source grant from this handle. It verifies only Pay's existing merchant/recipient and optional invoice-role facts. The actual Source still owns qualified bill provenance, issuer/store/member binding, independent submission permission, principal/read scope, Core registration/epoch/nonce, proof trust, request lifetime and all real authorization.

Call the constructor once during original `productAssociation` acquisition, outside every Pay Store lock. It uses the existing authorized `Store.View`. Active merchant identity/payout must match; if `invoiceMemberRequired` is true, the exact encoded native principal's original `MerchantMembers` row must be active and hold the existing invoice permission (owner or finance), with exact merchant/account fields. For a separately authorized product bill reader the false branch checks association only; it does not acquire a member role or invent read scope. Caller strings, booleans and snapshots grant nothing.

Retain the returned opaque handle in the actual Source lease. Its `Current() error` performs only one atomic load and immutable generation lookups. It takes no Store lock, calls no `View`, callback, network, FD operation, JSON parser or disk reader. It may be called inside the original Pay `Store.View/Update` and as part of the existing `NativeInvoiceSourceSnapshot.Current` / `NativePayAuthorization.Current`. A zero/nil handle is refused. Never call the constructor from `Current`.

Original authenticated Store open/cold decode initializes this in-memory projection from the original durable rows. Both root Store.Update and the existing request-scoped Store.Update publish it after successful original persistence and before `afterCommit`, unlock and successful return. This is the Store authority commit linearization point. A concurrent Current that overlaps an in-flight revocation can linearize before that commit; every subsequent Current sees the committed revoke. It does not claim a lock-free distributed/file-system lease or atomically cover a future network write. The original Source/transport/Auth effect boundary must still recheck its actual current permissions immediately before sending.

Merchant identity/central association/payout/status/creation and member identity/account/role/status/creation/update changes produce fresh per-row generations. Removal/recreation and revoke/regrant never revive an old handle. Unrelated bill/outbox/progress writes preserve the existing generation. Other merchants/members are independent. Failed persistence does not publish an uncommitted revoke. No persistent schema field, protocol wire, grant, approval, balance, signing key or extra transaction journal is added. A fresh process captures a fresh local handle from its authenticated original Store; old Source lifetimes must be retired by their existing owner rather than transferring a handle to a replacement Store/runtime.

Pay's existing `registeredNativeInvoiceIntentSource.ResolveInvoiceIntent` now composes its original independent `Current` with this same actual Pay fence, so a valid initial role cannot survive a late member revoke into a later Store mutation. Stale fences remain the original Native authority503 refusal on private HTTP routes. Auth independently embeds the handle in its existing `Authorize` and original intent Source paths, choosing the same `memberRequired` semantics it already owns; it must preserve independent submit and bound-invoice read scope.

Auth must combine this with LINK's actual same-original-request lifecycle callee that performs no FD I/O. The existing `LocalCaller.Current` fresh OS polling/peek is not safe to pretend is no-I/O under Pay's Store lock. LINK supplies `CurrentOriginalCaller(*http.Request) error` on the original private LocalCaller; full capture/refresh still happens outside Store locks. This fence itself does not mint that caller or replace LINK's request identity, lifecycle or Source trust.

The actual complete LINK successor is `640c67e8739f087cc78c060bd45f91381c3a9998` (`internal/securelink`, including eb59). A separate prepared P06 composition consumes that complete package, preserving the old d6 composition. `PAY_NATIVE_WORKFLOW_SUITE=merchant-fence-link` runs the new Pay-owned actual Unix caller/Store combination under the race detector, with `PAY_NATIVE_CALLER_SOCKET_ROOT` set to an owned short external socket root. It captures the original OS caller/body outside Store locks, consumes the normal decoder, checks `CurrentOriginalCaller(sameRequest)` AND the Pay role fence inside the actual Store.Update, then commits a role revoke while that original request is still active. Its next final commit refuses503 and retains no forbidden mutation. This is new cross-owner functional evidence, not a repeat of LINK's old groups, a business Source grant, a fresh remote-close detector, signing or funds proof.

Focused controls cover lock-safe Current inside original Update, revoked-before-final-commit denial with no mutation, cold durable revoke, scoped commit publication before afterCommit, revoke/regrant, role-independent association read, failed persistence, concurrent readers/writers, and actual registered intent/private HTTP refusal. They use explicit fact/Source fixtures and send no funds. The existing original test runner supports `PAY_NATIVE_WORKFLOW_SUITE=merchant-fence` with external TMPDIR/GOTMPDIR/GOCACHE; it runs only the relevant Go delta under the race detector. Previous 100/30/70 money and cryptographic suites are reused, not rerun as evidence for this Store change.
