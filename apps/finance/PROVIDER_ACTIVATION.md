# Controlled activation — NOT a live trading runbook

1. Keep `FINANCE_TRADING_ENABLED=false`, `FINANCE_SANDBOX_WRITES_ENABLED=false`, `FINANCE_LIVE_ENABLED=false`. Existing Finance keeps working. No RPC changes are needed for Broker integration.
2. Supply only a server Secret Manager reference or protected service configuration location, never credentials in chat, Git, browser variables, logs or command arguments. Copy the variable names from `.env.example`; do not dump a populated env. Select the actually provisioned Broker authentication method; personal Paper keys are not substitutes.
3. Set testnet/6423 + sandbox and the exact schema origins. `private_key_jwt` currently fails unsupported. Restart the Finance service through its normal authorized owner deployment; there is no hot reload or implicit activation.
4. From `apps/finance`, run `npm run finance:doctor`. This checks configuration only, makes no network call and prints safe fixed diagnostics. Disabled is not healthy/authenticated Sandbox. Missing credentials or owner verification context keeps the corresponding verification blocked.
5. Only with permission to test the supplied credentials, set `YNX_FINANCE_BROKER_VERIFY_ACCOUNT` to one persisted owner mapping and run `npm run finance:doctor -- --network-read-only`. This bounded read path acquires a token, lists assets, resolves that exact owner, reads its account/cash/buying power, positions and all bounded order pages, then obtains one tradable-asset quote. It uses the configured Broker-read and Market-Data rate gates, has no automatic retry and performs no account creation, funding, POST order or DELETE cancellation. `npm run finance:sandbox:verify -- --network-read-only` has the same read-only boundary. Neither command proves official Sandbox completion.
6. Run `npm run finance:sandbox:activation-plan` to inspect configuration-only prerequisites. It always remains blocked because configuration alone is not execution readiness. Before any write authorization, set an exact absolute `YNX_FINANCE_STATE_PATH` plus one canonical `YNX_FINANCE_BROKER_VERIFY_ACCOUNT`, then run `npm run finance:sandbox:activation-plan -- --local-read-only`. This credential-independent inspection performs no provider request and no state write. It verifies the existing file or PostgreSQL state without creating a file, table, migration or bootstrap row, then returns only non-sensitive counts for owner mapping, verified Wallet key, approved orders, execution-requested outboxes, ambiguous orders and reconcile-only orders. A controlled write requires official Sandbox credentials and entitlements, a persistent owner mapping, canonical server fee inputs, an exact Wallet-approved order whose approval was consumed, `FINANCE_SANDBOX_WRITES_ENABLED=true`, the matching 64-hex activation receipt and a separate immediate one-shot authorization. `SANDBOX_WRITE_CONFIGURATION_READY_NOT_EXECUTED` is possible only when the local read proves one exact `execution_requested` outbox and no ambiguous order; it still does not prove provider access or submit anything. The controlled worker alone may claim that queued request through `dispatch-one`. The separately authorized `verify-approved` command remains an operator verification sequence and records its own execution request before provider POST dispatch, provider query/reconciliation, provider DELETE cancellation and final reconciliation under `SANDBOX_VERIFY_APPROVED_ORDER_ONCE`. Provider raw status, provider order/client IDs, bounded HTTP request IDs and SSE cursor are persisted as distinct audit values. Unauthorized or incomplete preconditions fail before provider write.
7. Browser challenge/callback routes create and consume Wallet review evidence; the execution-request route only queues an approved owner-scoped request. Browser code never receives provider credentials or calls the provider. Public deployment is an independent external gate, not a prerequisite for a separately authorized local controlled Sandbox verification. Keep simulated USD/equity separate from YNXT; never claim an off-chain order has a chain transaction hash. Complete restart, terminal rejection, ambiguous-order reconciliation, partial-fill and cancellation-race review before public activation.

Rollback: set the module flag false and restart only with deployment authority. State v2 is a lazy, non-destructive migration from v1; take an authenticated backup before deploying it. An older binary must not overwrite a state file after v2 has been written. Public release and secret installation are not performed by the development/test commands.
