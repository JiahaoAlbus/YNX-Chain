# Finance Phase3 stdin deployment lease successor

Central's latest Phase3 review found that a real manual rollback after a successful deployment could not enter the old restore path: deploy mode correctly requires absent release paths, while a later rollback necessarily starts from exact present release objects. Reusing the deployment lease for that later action would also fail to bind the successful runtime state.

This successor separates the two modes. Deploy still requires all lease-owned stage, backup, release and release-container paths to be absent. It creates the release container no-replace, verifies the signed path/UID/GID/mode, moves the candidate, and emits parent tuples, the container's stable identity/empty/present tuples, the backup tuple, the candidate release tuple/inventory, and candidate service PID/NRestarts.

A later external or browser verification failure requires a wholly new Central-signed `FINANCE_ROLLBACK_FIRST_PRODUCTION_MANUAL_ROLLBACK` lease built from that immutable success receipt. Rollback requires the exact present container, release inventory, backup, candidate current link, candidate environment, unit/Caddy hashes and service PID/NRestarts. Every check uses an explicit fail-closed guard before the first write; it does not depend on implicit shell error behavior. Only after all checks pass does it restore the old runtime and remove the exact release plus exact empty container.

Before deploy begins, any partial placement is removed only when the exact created file identity still matches. Automatic failure rollback retains the same exact cleanup rules. The actual-shell suite now additionally performs a real successful deploy, simulates the later external-verification boundary, creates a separate signed-style rollback lease, invokes the real executor in rollback mode, and proves exact old-runtime restoration and release/container cleanup. Foreign inventory and substituted-release variants fail before mutation and remain preserved. The exact stdin bootstrap plus real executor cross-stage fixture still passes.

This remains a request only. Fresh public `/version` and `/health` were read without SSH and still report the old `3b2383f5...` runtime. Central must independently rerun all fixtures, fresh-read every production tuple, construct the exact signed lease, and freeze every literal command/argument before issuing a wholly new single-use lease. No production SSH, deployment, restart, current/unit/Caddy write, account request, signing or transaction occurred.
