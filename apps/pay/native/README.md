# Native Pay client and normal Main entry

This client reuses Pay's original private HTTP service and Wallet Main's original review/journal. The same module now has a macOS SwiftUI entry and an original Main boot controller. It owns no signer, balance store or transaction state machine and does not modify frozen Expo/Web pages. A locally installed QA app is separate from a qualified Main/Source connection and actual merchant/payment/refund acceptance.

Normal Main imports `createNativePayMainEntry({getMain,getContext})` from `main-entry.mjs`, calls its boot-only `compose(originalSource)` and connects only `invoke/status/cancel` through its existing safe live-frame IPC. Source supplies the original `pay`, synchronous `current` and existing archive/notification readers. Input has exact DATA shapes; no approve, key, send, capsule, URL or Source-construction operation exists. `broadcast-review` reads the exact retained original and requires P01's fixed `requestPQPayBroadcast(reference)` entry. That new entry is an owning CODE dependency until P01 supplies it; the generic Core `requestPQBroadcast` is never used as a fallback. The returned actual review must bind both hashes/account/operation/kind and leave approval in the original queue. Cancel calls the original Main rejection behavior and preserves the first real cause. The existing Main/Auth pipeline must dispatch the one original Member to Pay, retain actual `/v5/...` response bytes and keep UNKNOWN query-only. The full current contract is `internal/payproduct/V5_MAIN_PAY_DISPATCH_CONTRACT.md`; Core-target UNKNOWN must never be moved or sent to Pay.

Build the native app with `node scripts/build-qa.mjs /absolute/external/output --mac-app`. This extends the existing builder: exact Node/libnode, six original modules, native executable, source metadata, ad-hoc local QA signature and installer. Set TMPDIR/CLANG_MODULE_CACHE_PATH/SWIFT_MODULECACHE_PATH to owned external paths. Only standard Swift-driver transient files use an owned, cleaned OS temporary directory under the explicitly recorded bounded resource exception; outputs/caches/logs stay external. Install with the package's `bin/node install-mac-qa.mjs /absolute/new/versioned/qa-install-root`. It preserves existing apps/profiles, verifies signature and executable/source identity after copying and runs the installed executable's `--self-check`. It never overwrites Wallet or claims a production signature/notarization.

The optional `--main-runtime-manifest /absolute/original-owner/bridge-manifest.json` packages only the original owner's pinned JavaScript IPC bridge closure: `{entry,files:[{path,sha256}],originalOwnerInputs}`. Paths are relative source files under that manifest; Native images, keys, profiles and arbitrary symlinks are excluded. The bridge exports `openNativePayMainEntry()` and opens the already protected original Main/Source service, retaining that owner's actual peer/session/current checks. Build metadata grants nothing. Every selected dependency is checked before import. No environment variable, runtime-file chooser or public flag can activate it. With no actual bridge supplied, `desktop-runtime.json` deliberately contains `runtime:null`; the installed UI shows unavailable and disables business review controls. This is the current honest runtime boundary, not a demo or substitute Source.

`node cli.mjs --help` and `--diagnose` run without Source or network. An explicit original runtime is required for business commands:

The actual runtime module exports `openNativePayRuntime()` and returns:

- `current()`: original synchronous actor/account/session/epoch fence.
- `pay`: `createPrivateNativeInvoiceClient({origin, requestPrivate})` using the original qualified fixed-origin service transport. No fetch/TLS or service-credential fallback is included.
- `main`: the original protected Main facade exposing `requestPQTypedAction`, `reject`, `vault.status` and original `transactionSender.submissions.intentStore`. It may bridge the existing protected IPC but must not fabricate pending requests, store results or approval.
- `readInvoiceOriginals(subject,current)`: original Main/Source read-only archive. It returns exactly Main's existing `invoiceOriginals` shape: `{termsMessage,settlement}`. Refund `settlement` contains original `{review,member,original:{reviewSnapshot,signingSnapshot,selectedBinding}}`; no current nonce is decremented and no payer review/snapshot is invented from a Pay DTO. Missing archives close only that review.
- P01 `main.requestPQPayBroadcast(originalReference)`: required fixed Pay review entry, currently awaiting the original owner implementation/freeze. It must bind the original journal's Pay target and use the existing separate Wallet approval/Native pipeline, durable UNKNOWN and one Pay Packet dispatch. A generic `withSubmissionApproval(reference,send)` runtime callback is no longer consumed. `terms-submit`, `pay-submit` and `refund-submit` compatibility commands request this review only; they never execute approval or send. Missing this callee returns `NATIVE_PAY_MAIN_PAY_REVIEW_UNAVAILABLE`.
- optional `close()`: original owned resource cleanup.

The existing `events` command adds durable notification recovery to the same client. Its optional runtime ports are:

- `notificationInbox`: `new NativePayNotificationInbox('/absolute/private/external-path/inbox.sqlite')` imported from the packaged `lib/notification-inbox.mjs`. The runtime owns opening/closing it. Use an owned private directory (0700) and database (0600); never a different product's database. A mismatched/corrupt database stays unavailable and is preserved for recovery, without reset or automatic migration.
- `readNotificationScope()`: the original Source returns `{source,principal,genesis,bindingDigest,current}` for its actual authenticated binding. `current()` must synchronously throw on retirement/account/session/epoch change and return `undefined` while current. These are not inferred from event contents or CLI input. Different bindings have separate inbox partitions.
- `refreshOriginalProduct(eventReference,current)`: original Source/Cloud/Shop **read-only** lookup of `sourceOrder`, returning `{sourceOrder,queryOnly:true}` only after the original order is observed. Call `current()` around the await. Never invoke create, reprice, approve, pay, refund, or broadcast from this callback. Callback money/status fields are ignored.

The service exposes `GET /v5/pay/invoices/{merchant}/{invoice}/events` behind the existing private Source read authorization. It references only independently proven confirmed effects, using the same original Core event claim identity and retained root webhook identity. Unknown/failed operations and webhook replay children do not create events. The client reads the authenticated original bill, stages only bounded immutable event references, checks the same original confirmed operation/effect, performs the original product lookup, commits notification progress and rereads Pay. Source revocation clears private UI state. Missing cross-product readers preserve pending references across cold restart; repeated successful refreshes deduplicate. A crash after lookup may repeat the read-only lookup; this is not exactly-once cross-product delivery. No webhook secret, balance, Member, Source grant or retryable funds operation is cached. Inbox progress never marks a bill paid, supplies finality, or replays UNKNOWN.

Normal Main/SDK resolution for `@ynx-chain/wallet-auth` must come from that admitted original runtime/SDK image. The client consumes its sole codec and Main's existing invoiceOriginals review port. It does not copy or supply a new ABI/signer/provider. The actual approval remains in the existing Wallet UI/Auth; this CLI has no `approve`, key-import or raw-Member-paste command.

The workflow is intent → merchant review → original retained Member → original RegisterTerms → original terms recovery; payer invoice review → original Member → Pay settlement; merchant refund review → original payer-bound Member → refund; original hash query/reconcile after any uncertainty. Receipts are authenticated Pay projections, with `clientIndependentFinality:false`; the service's original H/H+1 verifier owns funds confirmation. Summaries omit full Member/envelope/policy material. Cold clients recover by server/Main references and create no new local transaction journal.

Normal product-intent consumption uses `createPrivateNativeInvoiceClient.createInvoiceIntent(originalRequest,current)` and `lookupInvoiceIntent(theSameOriginalRequest,current)`. The former makes one prepare-only POST; it never signs or submits a Member. The latter uses only `/v5/pay/invoice-intents/lookup` and cannot create. Source refusal503 `NATIVE_PAY_AUTHORITY_UNAVAILABLE` and request rejection409 `NATIVE_PAY_REQUEST_REJECTED` retain their actual code/status/path. Successful PREPARED/ISSUED views remain non-payment DATA and must match the exact original request/operation/Money terms.

The normal Main controller accepts `{action:'create-intent'|'lookup-intent',productId,sourceOrder}`. It obtains the complete retained original request through the Source-owned **DATA reader requirement** `readOriginalInvoiceIntent({productId,sourceOrder},current)`. This port must read the original product journal/order/bill, never current catalog prices or reconstructed approvals. It does not itself grant Source authority; missing actual reader returns `NATIVE_PAY_PRODUCT_ORIGINAL_UNAVAILABLE`. The renderer cannot supply amount, recipient, nonce, credentials or Source. Lost creation acknowledgement uses the same original product reference and lookup in a cold client; the originating product's existing journal retains its original attempt/request. No local second transaction journal or automatic create retry is introduced.
