# Wallet capability parity

Current executable parity is Create, Import/Offline Recovery, multi-account rename/switch/remove, default `ynx1` and internal `0x` compatibility, authoritative Testnet balance/activity, receive QR, signed send, exact authorization review, AI explanation boundary, Connected Apps/Sessions/Devices empty and failure states, audit, biometric gate, background lock, clipboard/screenshot privacy, 12 locales, RTL, light/dark and accessibility semantics.

The Android-owned standard Wallet layer now strictly approves one `eip155:6423` namespace and derived 0x account, answers standard account/network reads, and creates recoverable EIP-191, EIP-712 and EIP-1559 signatures only through an explicit lifecycle/approval/secret boundary. The official Reown WalletKit adapter provides v2 QR/manual pairing, explicit proposal/request approve and reject, session disconnect, SDK persistence restoration bound to the exact account, and strict chain-identity verification before raw EIP-1559 broadcast. The isolated HTTPS DApp Browser provides an EIP-1193 bridge with explicit `eth_requestAccounts` origin approval, 4100 before authorization, separate signing review, navigation-drift cancellation and no shared cookies. Missing relay configuration degrades only WalletConnect; Gateway and Product Sessions are never consulted. Installed relay/callback and first/external-party DApp completion remain unproven.

Protocol-level candidates now cover UserOperation envelopes, Product/merchant/developer/first-action sponsorship budgets, exact Paymaster/EntryPoint/target/selector constraints, Quant/Exchange/DEX mandates, capital product review and selective-disclosure Credentials. They are implemented and tested in `packages/wallet-auth`; they are not yet central-deployed or exposed as a completed on-chain Wallet flow.

Unproven parity remains passkey enrollment on installed devices, deployed Bundler/Paymaster, Guardian recovery, batch execution, stablecoin gas, hardware signer, contract simulation against a deployed node, WalletConnect installed relay/callback compatibility, installed DApp Browser first/external-party interoperability, persisted browser pending requests, live capital positions/exit queues, physical-device accessibility, production signing and stores. Each remains false in release evidence until direct proof exists.
