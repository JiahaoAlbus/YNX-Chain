# Code maintenance and recovery

The gateway closes admission synchronously on SIGTERM, SIGINT, or SIGUSR2. New HTTP work and WebSocket upgrades receive 503. `/healthz` remains readable and `/readyz` becomes 503. SIGUSR2 leaves the process available for health observation; restart is required to resume. There is no public maintenance mutation endpoint. Repeated signals join the original maintenance operation.

Accepted HTTP requests remain counted until both their handler and response settle, including handlers whose client disconnected. Accepted agent work may finish nested AI or language operations during the drain interval. After its deadline, cancellation removes queued work and aborts active work. A cancelled mutation reports `automaticRetry: false` and `outcome: reload-before-retry`: inspect the saved workspace/run before explicitly approving a retry. It does not assert that the mutation never happened.

The default drain interval is 30 seconds, followed by 10 seconds for cancellation. `YNX_CODE_DRAIN_TIMEOUT_MS` and `YNX_CODE_CANCEL_TIMEOUT_MS` accept 10–120000 milliseconds each. The checked-in systemd unit uses `TimeoutStopSec=75`; a deployment that increases application deadlines must increase the outer deadline accordingly. The previous 15-second unit is insufficient. A deployment must also preserve the state directory and its private permissions.

HTTP accounting covers compilation/tests, AI, agent, workspace, Git, environment, extensions, memory, chain, Wallet readiness, runtime-profile operations and assets. AI and language operations, queued/running compilation, Git operations, and terminal/debug/collaboration startup and final persistence have separate counters. `/healthz.active` and `.queued` keep their original **local compilation/test** meaning. The new `activity` object reports category counts, cleanup failures and the scope of those observations; counts are not user lists. Cloud operations routed through runtime profiles are also counted as HTTP `runtime` work. External model-server queues and applications launched inside persistent remote runtimes are not globally drained by this gateway.

The gateway waits for real local child `close`/PTY exit before removing workspaces or releasing their leases. Terminal final snapshots and collaboration SQLite writes settle before stores close. Agent interruptions are appended to durable run history. A timeout, unreaped child, or failed interactive persistence produces a failed receipt and exit code 1; databases are not deliberately closed beneath outstanding handlers. This is bounded failure reporting, not a guarantee that arbitrary remote work can always be cancelled. systemd may ultimately terminate an uncooperative process at its configured deadline.

Receipts are fsynced to `STATE_DIR/maintenance.json` with counts and source identity. `cleanShutdown: true` means the gateway's observed admitted work completed or its cancellation settled and its stores closed. It does not establish that persistent cloud applications or an upstream hosted model have exited, certify capacity for an arbitrary number of users, or prove installed Windows/mobile behavior.

## Recovery protection

Private terminal workspaces now live below `STATE_DIR/terminal-workspaces`, not an expendable temporary directory. A synchronization conflict retains a full `STATE_DIR/terminal-workspaces/.recovery/SESSION_ID.json` snapshot with the original owner, project, revision, session and payload. A collection or stop-verification failure retains a manifest with `payload: null`; **that manifest is not a backup of remote edits**. The remote workspace remains the authoritative recovery source. Recovery files are 0600 within a private sibling directory outside the user-writable terminal mount, created exclusively and never served by the gateway. User-created files or links in the workspace cannot select the recovery target.

Runtime profiles add an owner/runtime/token-scoped `terminal_recovery` SQLite table. Despite the historical table name, it protects remote terminal, language and debug operations. The marker is committed before remote preparation. A full saved snapshot or successful verified process cleanup may acknowledge only its own token. A stale acknowledgment cannot remove a newer guard. Pending recovery blocks another preparation, tasks, packages, previews and deletion of that runtime/profile after restart. Owner inventory exposes only `recoveryRequired`; another owner cannot inspect or delete it.

**Temporary remote restriction:** the current production LXD/SSH adapters do not provide a verified `assertStopped` contract for all remote writers. Exiting their local transport is insufficient. They therefore retain the guard and workspace, report recovery required, and make maintenance fail rather than collecting/acknowledging a potentially changing directory. This applies after ordinary remote interactive completion as well as maintenance. Local PTY and local language/debug paths retain their normal flow. A runtime with pending recovery must not be reused by another API path.

There is currently no user-facing automatic recovery action. An operator must preserve the original private state and remote directory, verify the original owner/project/runtime, inspect and stop the actual remote writers, collect a complete bounded snapshot, resolve any revision conflict without overwriting the newer workspace, and persist/verify the recovery result before clearing the exact marker. Do not delete the marker merely to reconnect. Recovery must also account for secrets held in temporary SSH credentials and remove those credentials only after the recovery connection is no longer needed. Operator assistance remains necessary for this temporary state.

**Rollback constraint:** the predecessor 6f runtime does not understand this new guard table. Starting that version against a state directory with pending guards can bypass the protection. A release/rollback procedure must read back the guard count and refuse such a rollback until those exact recoveries are resolved or the affected runtimes are otherwise isolated. Do not restore a stale state directory to erase guards or user changes.

## Required next work

1. Implement and validate a remote process lifecycle contract for LXD and SSH, including detached writers, process descendants, interruption during startup, and restart-safe verified cleanup. Add an authenticated owner-bound recovery UI/API that preserves revisions and never silently discards files. Until then remote interactive workflows and production lossless maintenance remain incomplete.
2. Validate this source as a new Linux package and deploy with the required outer stop timeout and rollback guard checks. This source change does not itself publish anything or update Windows public metadata.
3. Continue realistic simultaneous-user capacity and security validation. Existing queue/ACL/concurrency tests are bounded evidence, not proof of unlimited throughput or absolute safety.
4. Continue the separately scoped Klein blue/white and favicon acceptance, plus the latest Wallet entitlement policy. This backend maintenance change does not alter or silently migrate Wallet identities, guest workspaces, or user files.

Regression fixtures use isolated state and random ports. They cover real SIGUSR2/SIGTERM/repeated signals, request-body races, malformed HTTP/WebSocket targets, late writes, actual PTY and child exit, failed save/collection, stale guard tokens and cross-owner restart protection. Real Linux toolchain fixtures are distinguished from synthetic remote adapters; a fake adapter that explicitly verifies its own synthetic process is not production SSH/LXD proof.
