# Music Web business integration

The original Music business interface is retained in `web/index.html`; its business controller is `web/business.js`, mounted by `web/app.js`. It uses the original Music API, store, track/playlist/usage/AI/settlement IDs and current visibility rules. No demo tracks, listener counts, AI answers or payment receipts are inserted in production.

The owned production Web entry now loads the real frozen 5c5e8a23 browser SDK through `web/canonical-release.js` and connects it to the original controller through `web/canonical-session.js`. This is source adoption; matching production authority and actual installed/public Wallet acceptance remain required. Standard EVM connection does **not** activate this controller. The original bearer/manual-signature controller is not restored. `activateMusicBusiness(request)` is an owned integration seam for the release owner's frozen adapter, not a new authentication protocol. `request(relativePath, fetchOptions)` must return a `Response`; it receives exact JSON body strings or original upload FormData, content type/idempotency headers and an AbortSignal. Paths are relative `api/...` on the Music Web service. The adapter must supply actual registered Music authority, session revalidation and method/path/body-bound canonical action proof using the agreed shared contract. Authentication and proof verification remain server authority.

Activation fetches `/api/me` before exposing a private business UI. Account changes and invalidation must call `invalidateMusicBusiness()`; this cancels requests and streams, closes dialogs, clears private visible state, stops audio and revokes blob URLs. The controller never writes browser credential storage or guesses a native/browser identity tuple. Page disconnect clears the controller's in-memory authority and UI; issuer revocation belongs to the shared adapter, and is not claimed by this local action.

Every response is fenced by the captured controller generation. Requests and body reads have the actual 30-second consumer deadline even when an adapter ignores cancellation. Private routes reject redirects and cross-origin final responses. Media reads are bounded to 64 MiB. JSON failures, failed writes and malformed snapshots do not count as success. Search races are fenced separately; library writes serialize against the latest successful snapshot. Edit dialogs keep failed drafts and confirm updates with GET readback. Track evidence uses text nodes.

AI is opt-in per explicit proposal and stream action, shows provider/model/context/estimate, supports cancellation, and requires audited final proposal readback before apply/reject. Pay intents require an explicit review link from a centrally linked settlement, with exact `ynxpay://settlement/review` route. Browser downloads verify SHA-256 and describe handing bytes to the browser download manager; they do not mark a device file as saved or mint an available offline record.

Multipart upload serializes its final boundary and immutable bytes once, then uses the actual SDK action proof or bounded body commitment for those exact original bytes. The adapter refuses unsupported signing; it never substitutes a JSON digest or an old V1 cookie. Upload retries are user initiated. Lost-response upload recovery remains unfinished. Playlist creation persists an account-scoped recovery intent before POST, reuses its original Idempotency-Key and body after failure or restart, and clears the intent after original GET readback. Android and Apple persist the intent in their existing account files; Web uses its own IndexedDB metadata store. Explicitly starting a new playlist retains any previously saved server record. The controller intentionally does not guess canonical account registration, signer APIs, issuance, revocation or package/deployment settings.

`node apps/music/scripts/business-web-check.cjs` exercises shipped UI through isolated browser fixtures. These prove frontend behavior only, not Wallet approval, canonical production authority, licensed public content, production provider results, device installation or formal public acceptance. The full Go Music suite separately exercises original store/API behavior. Formal acceptance requires the unique release owner to integrate the frozen shared contract and deploy, then a real same-account user flow on the formal entry.
