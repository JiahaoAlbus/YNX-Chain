# Migration and compatibility

The persisted metadata schema is now `schemaVersion: 7`. Startup accepts v1 through v7 only and rejects invalid integrity before any backup or mutation. A valid legacy state is backed up byte-for-byte to an exclusive versioned backup such as `state.json.v1.bak` through `state.json.v6.bak`, normalized, upgraded, integrity-signed, and atomically saved as v7. An existing backup must itself verify and exactly match the migration source. V3 introduced Cloud/Docs product binding; v4 added an initially empty, product-isolated usage ledger; v5 added product-isolated storage byte-seconds and explicit coverage timestamps; v6 added hashed-owner product-data erasure receipts; v7 adds version-specific hot/cold/archive lifecycle state and persistent transition history. Legacy objects are deterministically classified by kind, while ambiguous legacy AI jobs fail closed and require fresh consent. Historical traffic, storage time, erasure events, lifecycle transitions, provider evidence, tier changes and restore events are never invented during migration.

For v1-v6 metadata-only objects that have no immutable version record, v7 preserves the absence of bytes and leaves lifecycle summary fields empty. It does not manufacture a hot copy or provider-backed durability claim. A material object that declares bytes, a digest or a current version but lacks the corresponding immutable version record is invalid and startup fails closed. Existing v1-v6 immutable versions are normalized to the bounded legacy-compatible `hot`/`immediate` state because those bytes were directly readable before the migration; the migration does not claim provider-native tiering or replication.

Current API prefix is `/api/v1`. Additive response fields are permitted; clients must ignore unknown response fields. Requests reject unknown fields. Breaking API changes require a new prefix and a documented overlap window.

Recovery archives use `ynx-cloud-recovery/v1` and validate regular files, relative paths, uniqueness, byte size, SHA-256, state integrity, and an empty restore destination. Local backup/restore is exercised by `scripts/smoke.sh`. A restore of v1-v6 state repeats the same versioned backup, normalization, lifecycle validation and atomic v7 persistence rules before the service becomes ready.

Commit `7759586` changes new local writes from the legacy global digest path to an opaque owner+product scoped digest path without changing `state.json` schema. Existing version records retain their exact legacy `BlobPath` and remain readable, hash-verified, exportable, restorable, and safely deletable. New writes use the scoped path through an optional adapter capability; providers that have not implemented scoped writes continue through the legacy interface and must not be described as providing cross-owner isolation. No startup rewrite silently copies or deletes existing bytes. A later physical migration must use a verified backup, copy-and-verify each referenced digest into its scoped destination, atomically update metadata, preserve rollback evidence, and delete legacy bytes only after all references have moved.

Commit `d11c382` adds schema-v7 lifecycle fields to objects and immutable versions plus persistent transition records. The object-level lifecycle summary mirrors only the current immutable version. A transition binds exact account, product, object, version, digest, source ref, source class, target class and provider evidence. Shared physical references require copy-on-write before two logical versions diverge in class. `pending` or `failed` transitions remain unresolved and block permanent deletion and product-account erasure until a bound retry completes. Archive versions return `restore-required` rather than reading through an unproven provider state. Export manifest schema v1 now includes relevant lifecycle transition history for the authenticated product; this is additive metadata, not a new claim of provider execution.

User portability exports use a separate schema (`ExportManifest.schemaVersion: 1`) and contain immutable object-version bytes plus owner metadata, grants, relevant lifecycle transition records and audit records for the authenticated product only. They are user-facing exports, not operator recovery archives.

`ynx-cloudd -data <data> -rollback-state-v1 <new-file>` verifies the current v7 source, normalizes and validates it, strips newer product, usage, erasure-receipt, lifecycle-summary and transition fields through the legacy schema encoder, and writes a legacy-compatible v1 state to a distinct, nonexistent destination without modifying current state. Tests cover a real minimal legacy-v1 layout, byte-identical v1/v2/v3/v4/v5/v6 backups, product, usage-ledger, storage-time, erasure-receipt and lifecycle migrations, metadata-only compatibility, current→legacy rollback hashing, destination overwrite rejection, and tampered-source rejection.

Remaining compatibility proof: run the previous released binary against the generated rollback state, exercise a real old Web/native client against the API overlap server, define deprecation dates, and perform a provider-backed remote restore and lifecycle migration drill. Until those direct artifacts exist, migration readiness remains partial.
