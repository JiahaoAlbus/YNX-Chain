# Card TEST provider lifecycle

The Card service keeps the original v1 YNXT simulation separate. The v2 Immersve connector fixes the host to `https://test.immersve.com` and uses server-only credentials. It implements the documented `POST /api/cards` body (`cardProgramId`, `fundingSourceId`), `GET /api/cards/:cardId`, `POST /api/cards/:cardId/freeze`, `POST /api/cards/:cardId/unfreeze`, account card and transaction pages, and `GET /api/transactions/:transactionId`. A create response only supplies a card ID; activation is recognized only after a matching account, program and funding-source readback with `status: active`. A freeze is confirmed through `isBlocked`, which is independent of card `status`. The transaction reader includes `statuses=all` so reversed records are visible; list/detail agreement is marked separately from any funding or settlement authority.

All provider writes require both `YNX_CARD_PROVIDER_TEST_WRITE_ENABLED=true` and the separate Immersve Test operator gate. Both default to false. Card operation IDs are reserved in encrypted, synchronous SQLite state before an outbound attempt. A repeated ID returns its recorded result and never resends; transport and response uncertainty remain `UNKNOWN`, even after restart. The ten-operation cap is local and does not assert upstream idempotency. UNKNOWN create candidates from `GET /api/accounts/:accountId/cards` are explicitly **unattributed**; an operator must resolve them from provider evidence before any separate action. No real provider POST was sent for this implementation.

The owner, provider, program, TEST environment and external account are immutable Card registry bindings. A trusted operator must establish an existing account reference from independent owner evidence, then an entitled `GET /api/accounts/:accountId` must confirm the exact cardholder account, partner and TEST liveness. The funding source is separately checked against the bound account and claimed before requesting Wallet approval. Program metadata and terms must match an enabled TEST program. Old, disabled programs remain readable for their existing cards. The Wallet v2 request uses `create-provider-test-card` and binds all program, funding-network, asset, limit, terms, fee and account-reference details; only the accepted Wallet v2 verifier can accept its signed callback. `card:application:write` and `card:controls:write` are separate Product Session scopes.

The TEST program JSON is validated on startup: exact provider/environment, unique program and funding-channel IDs, funding network and asset identity, token contract, currency and precision, risk/terms hashes, and the SHA-256 of the exact fee disclosure text. The funding endpoint reports only the bound provider Funding Source balance in its configured provider currency and minor units; this is not a Card spendable balance or a YNXT/tUSD balance. A missing provider source or mismatched currency fails closed.

The hosted KYC session lookup needed to recover an uncertain start remains `BLOCKED_PROVIDER_SPEC_SESSION_LOOKUP`. A generic `GET /api/accounts/:accountId/kyc-profile` does not identify an unknown hosted session. The default server composition has no hosted KYC adapter/verifier and does not claim KYC approval. Provider credentials, owned TEST program, operator entitlement and exact account binding have not been configured or officially verified. PAN/CVV and identity documents are never returned by this connector, written to Card state or logged. The read model contains only a masked last four digits when provided by the documented non-sensitive card response.

The Card app now consumes the shared Wallet SDK's WebCrypto Product Session on the exact Card HTTPS origin, with explicit YNX Wallet authorization, cold callback restore and a fresh proof for each API call. Native uses the same accepted v2 SDK with `account:read`, `card:application:write` and `card:controls:write`; the Standard EVM wallet remains independent. The `Provider TEST Card` panel keeps the guest simulation visible, reads the server's enabled TEST programs and exact fee disclosure, creates local drafts, shows KYC state, handles a signed Wallet provider approval callback, and reads provider status, funding-source balance and paged transaction reconciliation. Freeze/unfreeze, the single create request and Finance sharing remain subject to their separate server gates and proof scopes. The Finance grant/revoke UI requests only `card:finance:share`, which is absent in the currently pinned registry and therefore fails closed until the Wallet-owned registry and live authority accept it. Web runtime identity and backend `/api/card/v1/version` must report the same 40-character source commit before any private Card API client starts. The public Card host, Wallet callback, provider entitlement and real-user flow have not been verified.

For read-only configuration inspection run `node --import tsx server/cardSandboxVerify.ts doctor` from `apps/card`. With a securely configured Card database and provider credentials, `readback` uses only provider GETs for an already linked application. A trusted local operator may use `bind-account` with `YNX_CARD_OPERATOR_OWNER`, `YNX_CARD_OPERATOR_APPLICATION_ID`, `YNX_CARD_OPERATOR_EXTERNAL_ACCOUNT_ID`, `YNX_CARD_OPERATOR_EVIDENCE_ID`, and `YNX_CARD_OPERATOR_CONFIRM='BIND VERIFIED TEST ACCOUNT'`; it changes only the local binding and performs one provider account GET. It must not be exposed as an end-user route. Neither doctor nor readback sends a provider POST. See `immersve-sandbox.env.example` for gate and program configuration names.

Finance can read the same Card-owned records through `GET /api/card/v2/integrations/finance/account`. Its dedicated server key signs the existing `YNX_READ_INTEGRATION_V1` HMAC canonical string for consumer `finance`, owner `card`, and that exact path; each nonce is consumed durably. A Card owner must separately grant `card:finance:share` through a fresh Product Session and explicit `POST /api/card/v2/finance-consent` with `consent:true`, allowed read scopes and an expiry of at most 30 days. `POST /api/card/v2/finance-consent/revoke` with `revoke:true` stops reads. Missing key, ungranted scope, expired or revoked consent fail closed. Finance never receives a Card user session, a synthetic spendable balance, or permission to mutate a card. The shared Wallet registry and Card UI must add the new scope and consent screen before a real grant is possible.
