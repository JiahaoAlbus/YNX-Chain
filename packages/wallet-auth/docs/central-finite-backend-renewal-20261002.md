# Finite identity renewal: confidential product backend contract

This candidate changes only Central identity `identity:read`. A Finance private ProductSession remains a separately signed approval with its original 240-second expiry. No identity family can authorize a private product scope, a transfer, or an automatic Wallet signature.

## Server authentication and activation

The operator provisions `YNX_CENTRAL_BROWSER_BACKEND_CONFIG_FILE`. It references an owner-only 0600 regular file with schema `ynx-central-backend-clients/v1`, `clients` (exact `{clientId,keyId,publicKey}` Ed25519 public-key records), and `familySealKeyFile` (an owner-only 0600 regular file holding 32 random server seal bytes). Missing configuration disables the confidential routes; browser headers, Host and clientId are not substitutes for authentication. Private client signing keys stay in each protected product backend, outside browsers, runtime volumes and extension hosts.

Every confidential POST uses canonical JSON, no Origin, Sec-Fetch or Cookie headers, and `x-ynx-backend-proof`: base64url JSON of exact `{version:1,issuer,audience,clientId,keyId,method:'POST',path,bodySha256,issuedAt,nonce,signature}`. Issuer is `https://wallet-auth.ynxweb4.com`; audience is that URL plus `/v2/browser-sessions`. Body digest is SHA256 of the canonical JSON body. Nonce is 32 random bytes encoded base64url. Issued time is an ISO timestamp within 30 seconds of the checked server clock. Ed25519 signature covers canonical JSON of the other proof fields. Durable nonce binding rejects changed-body reuse; exact committed retry is allowed only through the action's idempotency checks.

## APIs

- `POST /v2/browser-sessions/token-family`: ordinary exact PKCE redemption fields (`clientId,origin,redirectUri,code,state,codeVerifier`) plus a random `requestId`. Only a successful current code redemption and the already signed approved client profile can create a family. It returns the original identity grant plus `familyId,familyEpoch:0,refreshHandle,absoluteExpiresAt,idleExpiresAt`. Repeating the exact initial request recovers the sealed initial result only before that family has rotated.
- `POST /v2/browser-sessions/renew`: exact `clientId,familyId,refreshHandle,expectedFamilyEpoch,requestId`. Renew no earlier than one minute before the current access expiry. It rotates the handle and epoch and returns a new five-minute grant, capped by the original identity absolute/idle deadline, with the unchanged subject/account/generation/audience/approved profile/identity scope. There are at most 64 rotations per family. Same old handle, epoch, requestId and body recovers the exact committed sealed result after a lost response. A different same-epoch request returns `SSO_FAMILY_CONFLICT`; previously committed older handles return `SSO_FAMILY_REPLAY`. Neither creates another grant or silently revokes a legitimately racing family.
- `POST /v2/browser-sessions/activity`: exact `clientId,familyId,eventId,observedAt`. This is exclusively a trusted product backend's attestation of a genuine, bounded UI action. Never call it from polling, WS frames, model jobs, timers, extension traffic or renewal. Event time must be no later than now and at most 30 seconds old. Exact duplicate event is idempotent; changed time for the same event is rejected. It advances only this family’s own user-activity deadline and the central genuine-user activity within the original two-hour absolute ceiling. At most 128 events per 30-second retained window. An expired/revoked session cannot be revived.
- `POST /v2/browser-sessions/revoke-family`: exact `clientId,familyId,requestId`. Product logout revokes every family, grant and unused code for the same central session generation and client. It is authenticated independently of the access grant, so logout still works after five-minute access expiry. Other products remain unaffected. Central logout/account rotation invalidates all old-generation families.

All responses are no-store and have no CORS credential access. Grant and refresh-handle retry results are AES-GCM sealed inside the existing Central durable transaction. Persist the requestId and intended epoch on the consumer before sending; after uncertain network delivery, retry the same request before attempting a new epoch. Never convert conflicts, expiry, revoke or profile denial into a guest identity or local deadline extension.

## Developer integration

Keep the refresh handle and confidential key sealed in the existing backend SQLite record. Parent and core host cookies reference the same finite family through separate exact-host opaque records. Do not send grant tokens, handles or signing keys into the kernel, editor extensions, URLs, postMessage or iframe. Validate unchanged subject/account/generation/audience/profile and current local logout revision before atomically installing each delayed result. Update access guards on the existing runtime without restarting it or resetting its original runtime limit. An account-A response cannot revive an account-B/logout state. Closed parent tabs and third-party-cookie blocking must not prevent server-to-server renewal.

## Legacy adoption

Unadopted legacy clients retain their existing status/authorize/introspect activity behavior. Family-linked access grants never extend the new family’s independent user-activity deadline; legacy polling in the same central identity cannot keep a Developer family alive. Only clients with the real trusted UI activity adapter opt into token-family. This avoids silently expiring active legacy Finance/Exchange/Quant use before those consumers are upgraded. All families still share original account/generation/profile and absolute two-hour revocation.

## Durable rollout and rollback

Ordinary legacy requests retain durable schema1. Only the first successfully authenticated family transaction upgrades to schema2 (`families,backendNonces`) while preserving every original session, consent proof, code, grant, revision and clock highwater. Invalid requests do not migrate. After schema2 is committed, **never run the old 2d/5f Central store reader on that file and never downgrade the state**. A rollback must retain this candidate's schema2 reader and approved-profile/family guards; UI or product-code rollback may use that guarded Central runtime. Provision and verify the compatible fallback before admitting the first production family. Original state snapshots are audit evidence, not rollback authority. This candidate is not deployed and has no provisioned production confidential clients yet.

## Remaining acceptance

Source tests exercise actual durable restart/idempotency, expiry, replay, consent/profile, logout, activity and protected configuration. Public backend credential provisioning, Developer consume-and-rotate implementation, parent-closed editor continuity, trusted real UI activity and controlled runtime admission remain separate and unverified. Private product finite continuation needs new explicit Wallet consent with visible duration and original scopes; this candidate does not implement or imply it.
