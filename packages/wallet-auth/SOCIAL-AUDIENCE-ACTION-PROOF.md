# Social audience action proof contract

This additive API reuses Product Session v2's existing P256 HTTP proof domain and sender-constrained device. It does not grant scopes, extend service duration, replace introspection, create a relationship store, or authenticate a Matrix homeserver.

`client.createSocialAudienceProof({path, body})` and the browser adapter's identical method accept only POST `/social/v3/matrix/audience/resolve` or `/social/v3/matrix/audience/authorize`. `body` is the exact bounded (16 KiB UTF-8) canonical JSON object string which the caller will submit. Numbers must be safe integers within ±(2^53−1), in canonical decimal form. Unicode scalar strings, including literal U+2028/U+2029 and supplementary characters, retain exact UTF-8 bytes and UTF-16 key ordering; unpaired UTF-16 surrogates are explicitly rejected on both sides. Duplicate keys, escaped alternatives, reordered keys and trailing JSON cannot pass the exact-byte canonical check. Its transaction, action and audience fields are covered by the SHA256 body digest; changing or reserializing them invalidates the proof. The result contains:

- `introspection`: the original unused introspection proof/header/body over exactly `social.contacts`, `social.feed`, `social.messaging`, `social.profile` (sorted).
- `proofHeader`: a separate unused business action proof over the exact path/body, with a distinct nonce and at most 30 seconds before the existing session deadline.
- `body`: exact original business bytes. No private key, family handle or bearer credential is returned.

Both proofs refer to the same stored current session/account/device/tuple. Existing generation, network, persistent revocation, browser negative signal, stored-session readback and signing checks run before and after asynchronous signing. Missing feed consent fails closed; old five-scope grants remain unchanged. Signed-out or changed sessions cannot release either proof. No proof is consumed by this API.

The Social consumer sends `introspection.proofHeader` as `X-YNX-Product-Session-Proof-V2` and business `proofHeader` as `X-YNX-Product-Session-Action-Proof-V2`, with exact `body`, to the one selected route. Existing browser same-origin/CSRF/live actor account-generation checks remain mandatory. No arbitrary caller scope, account, owner, room, homeserver or revision becomes authority.

The Social Go handler first uses the existing `productsessionv2.Client.Authorize` with the exact four server-configured scopes to obtain the fresh active Session. It then calls `productsessionv2.VerifySocialAudienceProof(actionHeader, session, "POST", exactPath, rawBody, serverNow)`. Do not pass a decoded cookie, caller-provided Session or an old unvalidated session. This verifier uses the existing signature domain and exact tuple, device, account, session, method, path, bytes and deadline. Introspection continues to be consumed only by the existing authority path. The action proof must never be submitted to that path.

Verification returns `ActionAuthorization{Nonce, BodyDigest, SessionBinding, ExpiresAt}`. **Verification does not consume the action nonce.** The existing Social durable transaction must atomically consume the exact `(SessionBinding, Nonce)` before any private read or side effect, binding its original transaction identifier, digest, action, actor generation and current audience/room/member revision. Repeated proofs cannot create a second operation; exact idempotent delivery can only return the prior committed result under the original product contract. Different body/transaction/revision cannot reuse a prior approval. A crash must not separate nonce consumption from the protected transaction. The Social owner implements this in its existing store, without another shared replay or relationship database.

Session account is signed; Central browser generation is checked by Social's existing live actor binding and transaction. Product Session v2 does not acquire a fabricated generation field. Native proof-only mode remains separate from the centrally bound browser mode. Confirmed membership and existing MXID provenance still come from the original Social directory/room store, not this signature.

The checked-in Go test fixture is generated by the actual JS recoverable client with a dedicated deterministic QA account/device. It contains only its public session and proof, never a device private key or user data. JS tests exercise altered body/path, old scopes, expiry, sign-out during clock await and stored-session changes after signing; Go tests verify the actual JS signature and reject changed HTTP context, account/device/session, nonce/signature/deadline and noncanonical headers. These are source/engineering checks, not production Social or Matrix E2EE acceptance.
