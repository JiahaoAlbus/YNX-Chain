# Original V5 binary request to registered project Source

`currentExistingDeveloperPrincipalV5` authenticates a fresh original V5 request; `recheckExistingDeveloperPrincipalV5` only rechecks an already consumed original. Both use the SAME Host private credential inventory, original Root-registered project Source, and completion fence. They create no credential from a DTO and install no Root or Source. The original inner principal bytes and Root current evidence remain unchanged.

The explicit relay is POST `/v5/developer/original-http-principal`, Content-Type `application/json`, no query/fragment. Body is strict canonicalJSON with exactly `version`, `operation`, `requestId`, `method`, `path`, `bodyOriginal`, `contentType`, `proofHeader`, `expected`. Version is string `5`; operation is `authenticate` or `recheck`. bodyOriginal is canonical unpadded base64url of the entire original binary HTTP body, not an expected hash. Method/path are POST `/api/v1/ide/deployments`; expected is the existing independent registered-device exact17 tuple. Whole relay max 92274688 bytes; decoded body max 68288512. Old V1 string-body relay is unchanged and is never a fallback.

Result DATA has the original principal fields with transport version `YNX-ORIGINAL-DEVELOPER-HTTP-PRINCIPAL/v5`, plus actual `contentType` and `bodyBinding` (bytes/sha3_512/sha512). New projection retains the SAME original Source result and credential in the Host private delivery inventory. Data is not a Principal, grant, Source or Native admission; the Auth consumer must verify original Root role/current, all original identity fields, body digest, actual content type and triple binding, preserve unknown effects, and use pinned original transport. Actual protected Source/profile provisioning and consumer runtime acceptance remain required.

New tests use actual public V5 crypto/current/Host with an explicitly PUBLIC mocked Root boundary; they do not claim actual Root provisioning or real login. Legacy green groups are reused.
