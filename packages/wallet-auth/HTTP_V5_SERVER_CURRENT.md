## Actual old boundary and new explicit current runner

The inspected original `OriginalAccountPolicyOperation` requires `body:string`; `#withAccountPolicy` originally calls only `accountPolicy.run`; V4 Host limits body to a UTF8 string <=1MiB. That contract cannot represent this binary proof. This implementation adds the optional original deployment configuration field `accountPolicy.runBinaryV5`; old `run` and its inputs retain their behavior. There is no fallback through `run` and no fake `body:''`.

`OriginalAccountPolicyBinaryV5Operation` is exactly `{version:'5',requestId,method:'POST',path:'/api/v1/ide/deployments',bodyOriginal:Uint8Array,contentType,bodyDigest,bodyBinding,proofHeader,walletControlProofHeader:null,session,at}`. It carries a fresh owned byte copy to each original policy call. Mutation is detected against the captured signed unsigned body after the supplier returns. This current-policy runner must borrow the normal committed account observation, invoke the original synchronous continuation at most once, post-recheck and clean up its owned context, return undefined and preserve UNKNOWN/first causes. The SAME existing `#withAccountPolicy` machinery guards no-entry, double-entry, swallowed execution failures and substituted results. The binary mode chooses only this explicit runner; missing runner returns `ACCOUNT_POLICY_BINARY_V5_NOT_SUPPLIED` before device-current use. The existing `run` remains required for original legacy routes, not evidence that binary is supported.

Auth owns the actual protected Source/current runner and its normal supply. This patch supplies only its precise consumer contract. No test seam or DTO is installed as production Source. Actual Auth runner wiring remains unavailable until its owner supplies it.

## Registered-device server verifier

`verifyOriginalProductSessionHTTPProofV5(input)` requires exact DATA input `{headerName,header,request,expected,source,abortContext,at,consumeNonce}`. Request is exact `{method,path,bodyOriginal,contentType,requiredScopes}`; body is never converted to UTF8, replaced or omitted. expected is the original V4 full registration/current tuple and must come independently from the normal Auth issuer selection; it is not extracted from the incoming proof. This uses only the same server current Source ports `readCurrent`, `assertCurrent`, `readRegistrationOriginal`, `readSessionOriginal`. No `produceHTTPProof`, V4 GET issuance source, new key or signer is called. Existing Source tenure/release responsibility stays with its original owner; no new guessed release port is introduced.

The verifier captures exact enumerable DATA records/scopes and owned binary input with intrinsic buffer/byteLength/native set; Proxy/SAB/detached/getter/fake bytes are refused, hostile typed iterators/own buffer getters are ignored. It captures source method identities without invoking getters and detects changes during awaits. The exact frozen original AbortContext is used throughout; cancellation is checked around awaited Source/nonce work, including falsy reasons.

It parses the independently selected original canonical V4 registration and original session, binds full current tuple, generation/revision/digest, product/client/platform/application/origin/callback/account/device and session scope, active registered time/revocation/expiry, header session and registration, proof time against both session and registration, and actual body SHA256/dual Bind/Content-Type. It verifies the complete V5 N1/index0/empty-path dual PQ member against the current record's independent exact pair. It then passes the original replay row and the SAME held source/context to `consumeNonce`, rechecks current/source method identity and exact original session/registration after it returns. `at` is an explicit authoritative caller time snapshot, not ambient current authority; the Host checks its own fresh clock at policy/commit/completion boundaries.

`productSessionHTTPProofV5ReplayKey` is an internal durable replay namespace, not a signing domain or permission. On failure after consume, this function neither rolls back nor retries the caller's original transaction. Input proof/header/body and owned transaction evidence remain the original caller's custody; it creates no replay/resubmit API. Success is still DATA `{session,proof,replayKey,signatureVerified:true,dataOnly:true,authorized:false,nativeAdmission:false}` and cannot act as a Principal or Source capability.
