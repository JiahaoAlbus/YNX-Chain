# Endpoint Authority v2: read-only expiry and controlled release handoff

The currently reviewed staging root has `maxValiditySeconds=3600` and a signing key ending at `2026-10-01T20:51:36.961Z`. A successful one-hour manifest is a limited test window. Monitoring does not make private service continuously available.

Run `node scripts/ops/endpoint-authority-expiry-monitor.mjs --trust-root PUBLIC_ROOT --checkpoint ACCEPTED_CHECKPOINT [--last-known-config PUBLIC_CONFIG_SNAPSHOT]`. Use the existing protected public root and a reviewed accepted checkpoint projection. The command verifies the current public configuration using the original consumer verifier and actual time. It records only expiry, public source identities, accepted sequence/digest, fixed public asset hashes, and Gateway/Finance build metadata. Thresholds are 900/300/0 seconds. Failed verification or transport is unavailable; a previous snapshot may supply labelled historical expiry metadata, never current authorization. It neither writes checkpoint/time nor signs/activates anything. A timer may invoke this read-only command after separate operational installation review; no signing timer is implemented here.

Before the window ends, the existing operator must collect fresh actual Gateway version/health, Finance web byte hashes and its separate Go build commit, actual host registry/product policy and callback digest, and contract-only acceptance evidence. Unverified user/service/provider cells remain false. The unsigned payload must name the accepted predecessor and immutable expiry. Central independently reviews its exact canonical digest and receipt byte hashes. Only that approved digest can be issued once by the original protected issuer, verified, and activated as one compatible application/configuration group. A read-only monitor cannot accept the evidence or authorize issuance. On failure retain current compatible state and journal; application rollback never rewinds accepted history.

The original `assertAuthorityV2TrustRoot` supports versioned roots, explicit anchors, non-revoked Ed25519 keys with finite windows, consumer/product restrictions, and maximum manifest validity up to 604800 seconds. `assertAuthorityV2IssuancePolicy` still enforces the configured root limit and key window. These capabilities do not approve a different lifetime. A maintainable root/key rollover requires a separately reviewed exact public root, incremented root version, anchor tied to the accepted checkpoint/digest, protected signer custody/public-key correspondence, finite key windows, exact consumers/scopes, and an explicitly approved maximum validity. Protected reader ownership/permissions, monotonic checkpoint transition, trusted-time preservation, and current-reader rollback must be tested before activation. Keep the old key/root and history recoverable; do not overwrite existing custody or bootstrap from sequence zero. A longer window, root replacement, unattended issuer, automatic renewal, or weakening expiry is not implemented or authorized by this monitor.

Outstanding operations are the installed expiry alert/notification destination, fresh-fact collection/review ownership and response deadline, and tested root/key rollover handoff before key expiry. These are internal release/operations work, not Broker or Relay credentials. No public-user, financial-provider, or all-platform service completion follows from contract authority availability.
